# What does mcp do?

# What `docuharnessx.mcp` does

`docuharnessx.mcp` is the **stdio MCP refine server** for DocuHarnessX — a Model Context Protocol server that lets a human refine generated documentation conversationally from an MCP client. The module docstring states it is "the **single public namespace** for the interactive document-refinement MCP server" (`docuharnessx/mcp/__init__.py:1-3`). The workflow it supports is: after a batch `dhx run` produces a role-based draft — segments persisted as `<id>.md` under `<out>/segments` by `FilesystemSegmentStore` plus a built Material site under `<out>/site` — a human opens that output in an MCP client (opencode / Claude Code / Cursor) and refines the docs through the tools the package exposes (`docuharnessx/mcp/__init__.py:4-9`).

A defining design constraint is that the package is a **thin composition layer**, not a new engine: it reuses DocuHarnessX's existing modular core — the bounded agentic writer `AgenticProseRunner`, the deterministic structure gate `validate_agent_body`, the blueprint builder, the segment wiring and fallback renderer, the segment store, the assembler (`assemble_site` plus the per-target site-identity resolver), and the model resolver — and builds "**no** second generation engine and no RAG / embedding / vector index" (`docuharnessx/mcp/__init__.py:9-16`).

## Public surface

The package's `__all__` contract re-exports everything from its submodules: `RefineSession`, `resolve_session`, `planned_from_segment`, `build_overview_blueprint`, the eight refine tool handlers (`list_segments`, `get_segment`, `validate_segment`, `rewrite_segment`, `draft_overview`, `refine_overview`, `get_overview`, `reassemble_site`), plus `build_refine_server` and `run_stdio` (`docuharnessx/mcp/__init__.py:74-89`). Downstream consumers — the `dhx mcp` CLI launcher and the tests — import from this one namespace rather than reaching into submodules (`docuharnessx/mcp/__init__.py:18-23`).

## The server and dispatch

`build_refine_server` in `docuharnessx/mcp/server.py` constructs a low-level `mcp.server.Server` named `"docuharnessx-refine"` (`docuharnessx/mcp/server.py:54, 98`). Its key design choice: the workspace (target repo + output dir) is **set by the agent** via an `open_workspace` tool rather than hardcoded at launch; an optional pre-opened `RefineSession` supports the `dhx mcp <repo> --out` convenience (`docuharnessx/mcp/server.py:3-4, 88-99`). The factory registers a `@server.list_tools()` handler that advertises typed `mcp.types.Tool` descriptors from `docuharnessx.mcp.schemas`, and one `@server.call_tool(validate_input=False)` dispatcher that validates arguments, dispatches to the matching handler over the bound session, **offloads the synchronous model-touching handlers off the async loop via `asyncio.to_thread`**, wraps each handler's structured result as MCP content, and returns a structured tool error for a missing/malformed argument or an unknown tool — it never raises out of the dispatch loop (`docuharnessx/mcp/server.py:19-24, 128-201`). Argument validation is owned in the dispatcher (`validate_input=False`) so a bad call yields a clear, argument-naming error rather than the framework's generic JSON-Schema message (`docuharnessx/mcp/server.py:28-31`).

`run_stdio` drives the server over the stdio transport (`mcp.server.stdio.stdio_server` by default), awaiting `server.run(read_stream, write_stream, init_options)` until the client disconnects (`docuharnessx/mcp/server.py:206-234`). The server logs to **stderr** so stdout stays the MCP protocol channel (`docuharnessx/mcp/server.py:30-31, 50-51`).

## Session state

`RefineSession` is a dataclass holding the per-target state the handlers read: `out_dir`, `target_repo`, the loaded `Vocabulary`, the `FilesystemSegmentStore` rooted at `<out>/segments` ("the single on-disk source of truth"), the resolved `ModelConfig` (or `None`), the per-target `SiteIdentity`, an optional `RepoAnalysis` (defaults to `None`), and the `min_citations` bar (`docuharnessx/mcp/session.py:66-84`). `resolve_session` composes the existing core: it validates the target first via `_validate_target_repo` (raising `TargetRepoError`), defaults the output dir to `<target>/.docuharnessx/out` when `--out` is omitted, loads the project vocabulary, provisions the store, resolves the site identity from the target's origin remote via `resolve_site_identity` + `read_origin_remote`, and resolves the model — swallowing a no-model `ModelResolutionError` to `None` so the server still starts and the model-touching tools degrade explicitly (`docuharnessx/mcp/session.py:99-177, 43-44`).

## The tools

`docuharnessx/mcp/schemas.py` owns the static protocol contract: a `_TOOLS` tuple of `mt.Tool` descriptors — `open_workspace`, `list_segments`, `get_segment`, `rewrite_segment`, `validate_segment`, `reassemble_site`, `get_overview`, `draft_overview`, `refine_overview` — each with a name, description, and strict JSON-Schema `inputSchema` (with `additionalProperties: False`), plus `TOOL_NAMES` (the name set the dispatcher checks) and the structured error envelopes `make_tool_error`, `unknown_tool_error`, `missing_argument_error`, `no_workspace_error`, and `open_workspace_failed_error` (`docuharnessx/mcp/schemas.py:120-292`). The schemas mirror the handler signatures: no-argument tools take an empty object, `get_segment`/`validate_segment` require `id`, `rewrite_segment` requires `id` + `guidance`, and `refine_overview` requires `guidance` (`docuharnessx/mcp/schemas.py:15-21`).

Each handler in `docuharnessx/mcp/handlers.py` is a plain function taking the bound session and returning a JSON-serialisable mapping; a handler "never raises out of itself for an expected domain condition" — it returns a structured result (a verdict or an error envelope) so the dispatch loop stays alive (`docuharnessx/mcp/handlers.py:3-8`). The three read-only, model-free tools read only the session's store: `list_segments` returns every stored segment's `id`/`title`/`roles`/`intent`/`subjects` in the store's deterministic by-id order (`docuharnessx/mcp/handlers.py:198-209`); `get_segment` adds `summary` + `body`, and a missing id yields the structured `_missing_segment_error` naming the id rather than a raise (`docuharnessx/mcp/handlers.py:212-226, 94-106`); `validate_segment` runs the deterministic structure gate `validate_agent_body` over the body at the same `session.min_citations` threshold the rewrite path enforces, returning `accepted`/`mermaid_blocks`/`cited_files`/`reason` (`docuharnessx/mcp/handlers.py:229-252`).

The model-touching tools reuse the writer + gate. `rewrite_segment` reconstructs the same-id deterministic blueprint via `planned_from_segment` → `build_blueprint`, re-runs `AgenticProseRunner.run(blueprint, repo_path=session.target_repo, model=..., guidance=guidance, min_citations=...)` offloaded via `asyncio.to_thread`, and persists the new body **only** when the gate accepts it — writing through `_replace_segment_in_place`, which re-serialises to the existing `<id>.md` because `FilesystemSegmentStore` has no `update` method and `put` raises `IdConflictError` on an existing id (`docuharnessx/mcp/handlers.py:298-393, 260-290`). A no-model session returns the explicit `_no_model_result` instead of producing content (`docuharnessx/mcp/handlers.py:109-128`), and a rejected/failed run surfaces the gate verdict plus the deterministic `render_fallback_body` while persisting **nothing** (`docuharnessx/mcp/handlers.py:357-374`).

The overview capability drafts/refines a project-wide front-door document (Purpose / Use cases / Features / Design choices) through the same `_run_overview` core: build the overview-shaped blueprint, run the bounded writer, gate, and persist on accept as the reserved `overview.md` entry (`docuharnessx/mcp/handlers.py:424-531`). `get_overview` reads that persisted entry lazily and returns an explicit `exists=False` result when none has been drafted (`docuharnessx/mcp/handlers.py:534-559`). `reassemble_site` is the only assembling handler and is model-free: it builds a `ReviewReport` whose accepted set is the current store segments plus the persisted overview (adapted by `_overview_accepted_entry` so the frozen `assemble_site` can surface the role-free front-door page), calls the reused `assemble_site`, and writes only under `<out>/site` (`docuharnessx/mcp/handlers.py:670-736, 598-667`).

## The pure glue modules

Two pure, model-free modules feed the writer. `docuharnessx/mcp/planned.py` implements `planned_from_segment`, which reconstructs a stable-id `PlannedSegment` from a stored `Segment` by re-deriving the planner's deterministic `segment_key` (`"<roles>__<intent>__<subjects-digest>"`, with a `blake2b` digest over sorted canonical subject strings), guaranteeing the round-trip `segment_id(planned_from_segment(seg)) == seg.id` so a rewrite re-wires the same id in place (`docuharnessx/mcp/planned.py:12-23, 89-141`). `docuharnessx/mcp/overview.py` provides `build_overview_blueprint`, which produces the overview-shaped `CompositionBlueprint` whose four ordered chunk headings are `OVERVIEW_SECTION_HEADINGS = ("Purpose", "Use cases", "Features", "Design choices")` and whose reserved id is `OVERVIEW_SEGMENT_ID = "overview"` (`docuharnessx/mcp/overview.py:100-112, 281-353`). Its `persist_overview`/`load_overview`/`overview_path` helpers write and read `<store_dir>/overview.md` using the store's own on-disk format `serialize_segment`/`parse_segment`/`to_segment`, so the reserved entry is read back lazily on every call (`docuharnessx/mcp/overview.py:375-440`). Notably, `guidance` is deliberately **not** folded into the blueprint — it reaches the agent only through `AgenticProseRunner.run(..., guidance=...)`, so the blueprint is independent of the guidance value and guidance never leaks out as a doc heading (`docuharnessx/mcp/overview.py:31-39, 314-317`).

## The CLI entry point

`dhx mcp` is a recognised subcommand (kept intact by the bare-form normaliser in `_SUBCOMMANDS`, `docuharnessx/cli.py:90-97`). `_mcp_command` guards the MCP SDK import with a dependency-naming `DependencyError` via `_require_mcp`, validates the target through the same `_validate_target_repo` the `run` path uses, resolves the per-target session, and launches the stdio server via `_run_stdio_blocking`, which wraps `docuharnessx.mcp.run_stdio` in `asyncio.run` and serves until the client disconnects (`docuharnessx/cli.py:719-779, 665-687, 704-716`). The target is optional at launch: when omitted, the client points the server at a repo/out at run time via `open_workspace` (`docuharnessx/cli.py:752-774`).

In short: `docuharnessx.mcp` turns DocuHarnessX's batch-produced, role-based documentation output into a live, tool-driven workspace — letting an MCP client list, inspect, validate, rewrite, and reassemble segments, and draft/refine a grounded narrative overview — all while reusing the existing writer, structure gate, store, and assembler rather than building a second generation engine.
