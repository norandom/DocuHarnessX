# Brief — comprehension-visuals

## Feature

Give readers **pictures and a domain glossary** that match the engineering-depth slider, not only file-level flowcharts. Follow-up to the v3.1.0 black theme + depth layers. Apply equally to ordinary software repos **and** quant / data-science / AI-ML projects.

## Who has the problem

Operators who adopt a documented project (depth 1–3) and programmers who work in it (depth 5–7). Maintainers of pipeline-heavy repos (Kedro, Airflow, notebooks, feature stores) whose “how does data move?” question is not answered by a file list.

## Current situation

The assembler already prepends deterministic Mermaid **flowcharts** (question → related pages → cited files, directory subgraphs). The substance gate *allows* mindmap, sequence, C4, pie, timeline, class diagrams — the assembler never **builds** them. Depth layers hide summary / diagrams / prose / grounding, but every diagram is the same kind. There is no project glossary, no in-page keyword highlight, no related-term browsing. MkDocs search is lunr (keyword, not semantic). Analysis does not detect pipeline DAGs or data lineage.

## What should change

1. **Depth-assigned diagram kinds** from grounded analysis (C4/mindmap at adopter depth, sequence/sankey/DAG in the middle, file flowcharts and dense DAGs at programmer depth).
2. **Visual Paradigm–style textual analysis analog** (not the VP product): a project glossary of terms + aliases + definitions; highlight occurrences in running text; each term links to a glossary entry that lists related terms and pages (semantic/related-node browsing).
3. **Search/index**: keep MkDocs search; add a glossary index that is itself searchable; do **not** claim embedding-based semantic search.
4. **Sankey** of “what data enters the entrypoint and where it goes.”
5. **Autogenerated DAGs** when a pipeline DSL is present; otherwise a coarse DAG from entrypoints → components → artifacts.
6. All new pictures are **deterministic and fail-closed** (omit the picture if it cannot be grounded), same contract as current graphs.
7. **Compliance self-assessment matrix** (reference, not a certification): at init / re-init ask which regimes apply (ISO 27001, PCI DSS, NIS2, CRA, GDPR, or none). Publish a pillar × regime heatmap: green / yellow / red from repo evidence, **gray if the regime or pillar does not apply**. Operator overrides stay in project files.

## Boundary Candidates

- In: assembler diagram emitters, analysis detectors for pipelines/lineage, glossary store + autolink at assemble time, depth assignment table, glossary index page, compliance interview + evidence matrix.
- Out: Visual Paradigm import/export, embedding/vector search, training models, replacing the substance gate, hosted graph databases, ISO/PCI/NIS2/CRA/GDPR **certification or audit opinions**.
- Adjacent: `mkdocs-site-assembler` graphs + theme + depth layers; `repo-ingestion-analysis`; `ontology-engine` vocabulary as a seed for glossary terms; living pages as the text that gets highlighted.

## Locked decisions

- Glossary is **assembled**, not a live NLP service. Seed from ontology roles/intents/subjects, detected components/public symbols, and operator-editable `.docuharnessx/glossary.yaml`. Highlight is case-insensitive whole-word (and aliases).
- “Requirements language” means: (a) glossary terms treated as the project dictionary, (b) if the repo already contains requirement-shaped sentences (EARS/`shall` in `requirements.md` / ADRs), surface them as **requirement cards** that link into the glossary — not a new requirements authoring IDE.
- MkDocs lunr remains the search box. Related-node browsing is the glossary graph + backlinks, not a second search engine.
- Sankey values: when true volumes are unknown, use **unit counts** (files, tables, hops) and label that they are structural, not measured throughput.
- DAG detectors are **allow-listed** (see design); unknown DSLs omit the DAG rather than guessing.
- Compliance is a **self-assessment reference**. Selecting a regime does not claim the project is certified. Unselected regimes render as a gray column. PCI-specific pillars are gray unless PCI DSS is selected.
