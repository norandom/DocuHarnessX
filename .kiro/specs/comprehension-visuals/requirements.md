# Requirements Document

## Introduction

Operators who publish a DocuHarnessX site, and readers who adopt or work in the documented project, currently get the same file-level flowcharts at every engineering depth. Adopters cannot see “what this system is” or “where data goes.” Quant, data-science, and AI/ML repositories are documented as generic software even when they are pipelines. There is no project dictionary: domain words in the prose are not highlighted, not defined, and not linked to related material.

This specification adds **depth-assigned comprehension visuals** (C4, mindmap, sequence, sankey, DAG, class/public surface, coverage pie, timeline, compliance heatmap) built from grounded analysis, plus a **Visual Paradigm–style glossary**: terms with aliases and definitions, highlight in running text, and related-node browsing through a glossary index. MkDocs keyword search remains; it is not replaced by embedding search. At init, the operator can name compliance topics (ISO 27001, PCI DSS, NIS2, CRA, GDPR); the site then shows a self-assessment matrix, not an audit certificate.

## Boundary Context

- **In scope**: deterministic diagram emitters assigned to depth layers; pipeline/DAG and data-lineage signals in analysis when files evidence them; project glossary (seeded + operator-editable) with highlight and related-term/page index; optional requirement cards from existing requirement-shaped sentences in the repo; sankey of entrypoint-centered data flow; autogenerated DAGs from allow-listed pipeline descriptions or a coarse fallback; applying the same pictures to ordinary software and to quant/AI/ML repos; init/re-init interview for optional compliance regimes; a self-assessment heatmap of shared control pillars vs those regimes (green / yellow / red / gray).
- **Out of scope**: Visual Paradigm product integration or SysML/ReqIF import; embedding- or vector-based semantic search; training or swapping the language model; changing substance-gate accept criteria for page *prose*; a requirements authoring IDE; inventing pipeline edges that are not in the repository; measured runtime throughput (volumes are structural counts unless the repo states numbers); claiming ISO 27001, PCI DSS, NIS2, CRA, or GDPR certification or producing an auditor-ready SoA.
- **Adjacent expectations**: existing depth layers (summary 1, diagrams 3, prose 5, grounding 7) stay; new pictures occupy those layers per the depth table. Living pages remain the prose source of truth and are not mutated by highlighting (assemble output is). Ontology vocabulary seeds glossary terms but is not the glossary. Analysis remains model-free. Fail-closed: no picture rather than an ungrounded one.

## Requirements

### Requirement 1: Depth-assigned picture kinds

**Objective:** As a reader, I want pictures that match how deeply I am reading, so that an adopter is not shown a file graph and a programmer still gets one.

#### Acceptance Criteria

1. When the published site is assembled, DocuHarnessX shall attach each generated picture to a minimum engineering depth from the locked table (C4/mindmap at 1–2, sequence and collapsed DAG/sankey at 3, public-surface/class at 4, file flowcharts at 5, denser DAG/sequence at 6, store-level sankey and requirement cards at 7).
2. When the reader’s selected depth is below a picture’s minimum, the site shall hide that picture with the existing depth mechanism.
3. If evidence for a picture kind is missing, DocuHarnessX shall omit that picture and shall not emit a template placeholder.
4. The DocuHarnessX shall keep emitting the existing file-level flowcharts at depth 5 when cited files or related pages exist.

### Requirement 2: Adopter and operator pictures

**Objective:** As an adopter or operator, I want a system-level picture and a typical-run sequence, so that I can understand the project before opening files.

#### Acceptance Criteria

1. When analysis yields at least one component or entrypoint, DocuHarnessX shall publish a context-level picture of the system (what it is and what it talks to) at depth 1.
2. When more than one component is detected, DocuHarnessX shall publish a container-level picture of those components at depth 2.
3. When an entrypoint or a typical run can be ordered from analysis, DocuHarnessX shall publish a sequence picture of that run at depth 3.
4. When accepted pages exist, DocuHarnessX shall publish a coverage picture (documented vs planned vs omitted) at depth 2.
5. When the project has an adoption record, DocuHarnessX shall publish a timeline of adopt → generate → sufficient (or stale) at depth 2.

### Requirement 3: Entrypoint-centered sankey

**Objective:** As a reader, I want to see what data (or input) enters the program and where it goes, so that lineage is visible without reading every module.

#### Acceptance Criteria

1. When at least one entrypoint is detected, DocuHarnessX shall publish a flow picture from inputs through that entrypoint to downstream stores, components, or outputs.
2. If the repository does not state numeric volumes, DocuHarnessX shall still draw the flow using structural counts (hops, files, or tables) and shall label the picture as structural, not measured throughput.
3. If no entrypoint and no data-path evidence exist, DocuHarnessX shall omit the sankey.
4. Where the repository looks like a quant, data-science, or AI/ML project (notebooks, data directories, training or feature-pipeline files), DocuHarnessX shall prefer lineage stages such as raw → features → model/signal → output when those stages are evidenced, instead of only source-file names.

### Requirement 4: Autogenerated DAGs

**Objective:** As a reader of a pipeline-shaped project, I want a DAG of the actual pipeline, so that task order is visible without opening the orchestrator UI.

#### Acceptance Criteria

1. When an allow-listed pipeline description is present in the repository (workflow jobs with dependencies, Makefile targets, or a recognized data-pipeline definition), DocuHarnessX shall publish a DAG of those tasks and their dependencies.
2. If no allow-listed pipeline description is present, DocuHarnessX shall publish a coarse DAG of entrypoint → component → artifact only when those nodes exist, or omit the DAG.
3. If a candidate edge cannot be grounded in a file or a declared dependency, DocuHarnessX shall not draw that edge.
4. DocuHarnessX shall show a collapsed named-stage DAG at depth 3 and a more detailed DAG at depths 4–7.
5. The DocuHarnessX shall not require a model call to produce the DAG.

### Requirement 5: Public surface picture

**Objective:** As an integrator, I want a picture of the public surface, so that I can see what I am supposed to call.

#### Acceptance Criteria

1. When public symbols or CLI commands are detected, DocuHarnessX shall publish a surface picture of those names at depth 4.
2. If no public surface is detected, DocuHarnessX shall omit that picture.

### Requirement 6: Project glossary

**Objective:** As a reader, I want domain words defined and findable, so that “account” or “signal” means what this project means.

#### Acceptance Criteria

1. When a site is assembled, DocuHarnessX shall publish a glossary index of project terms, each with a definition (or an explicit “undefined”) and optional aliases.
2. The DocuHarnessX shall seed glossary terms from the project ontology (roles, intents, subjects) and from detected component and public-surface names, without inventing definitions that are not in the repository or ontology.
3. When `.docuharnessx/glossary.yaml` is present and valid, DocuHarnessX shall merge operator terms (operator wins on definition and aliases).
4. If the glossary file is present but invalid, DocuHarnessX shall fail the assemble with a message naming the file, and shall not silently drop the glossary.
5. The DocuHarnessX shall keep the glossary as project files eligible for version control (not gitignored).

### Requirement 7: Keyword highlight and related-node browsing

**Objective:** As a reader, I want glossary terms highlighted in the prose and linked to related material, so that I can browse meaning instead of grepping.

#### Acceptance Criteria

1. When a glossary term or alias appears as a whole word in assembled page prose, DocuHarnessX shall highlight that occurrence and link it to the term’s glossary entry.
2. The DocuHarnessX shall not alter text inside code fences, inline code, or existing links.
3. When a reader opens a glossary term, the site shall show its definition, aliases, related terms, and the pages where it appears.
4. When a term has related terms, DocuHarnessX shall show a small related-nodes picture on that term’s entry.
5. The published site’s search box shall still find glossary terms and definitions as ordinary searchable text.
6. The DocuHarnessX shall not require a separate semantic-search service for related-node browsing.

### Requirement 8: Requirements language when present

**Objective:** As a reader, I want existing requirement-shaped sentences in the repo tied into the glossary, so that “shall” statements are not stranded from the pictures.

#### Acceptance Criteria

1. Where the repository already contains requirement-shaped sentences (EARS or “shall” statements in obvious requirements or ADR files), DocuHarnessX shall list them as requirement cards that link to matching glossary terms.
2. If no such sentences are found, DocuHarnessX shall omit the requirement-card section and shall not invent requirements.
3. The DocuHarnessX shall not provide an interactive requirements editor.

### Requirement 9: Fail-closed, deterministic pictures

**Objective:** As an operator, I want pictures to be reproducible and honest, so that CI does not publish decorative fiction.

#### Acceptance Criteria

1. When the same repository analysis and living pages are assembled twice, DocuHarnessX shall emit byte-identical pictures and glossary pages.
2. The DocuHarnessX shall not call a language model to invent diagram nodes or glossary definitions.
3. If a picture kind is not on the allowed diagram list, DocuHarnessX shall not emit it.
4. The substance gate shall continue to judge page prose independently of whether pictures were attached at assemble time.

### Requirement 10: Operator depth and theme stay in control

**Objective:** As an operator, I want new pictures to obey the existing depth default and theme, so that v3.1.0 presentation settings keep working.

#### Acceptance Criteria

1. When `.docuharnessx/site.yaml` sets a default depth, newly added pictures shall respect that default on first load.
2. When the reader moves the depth slider, new pictures shall appear or hide with the existing layers.
3. The DocuHarnessX shall not require a new init interview field solely to enable the non-compliance pictures; they assemble whenever evidence exists.

### Requirement 11: Compliance topics at init and re-init

**Objective:** As an operator, I want to say which compliance topics apply when I (re)initialize the document, so that inapplicable regimes stay out of the way.

#### Acceptance Criteria

1. When the operator runs interactive setup, DocuHarnessX shall ask which compliance topics apply, offering at least ISO 27001, PCI DSS, NIS2, CRA, GDPR, and none.
2. When the operator accepts the default or answers none, DocuHarnessX shall record that no regime is in scope and shall not paint those columns as failing.
3. When the operator later re-initializes setup to manage the project (without requiring a full living-page regenerate), DocuHarnessX shall re-ask the compliance topics and shall keep the previous selection as the Enter default.
4. When `--default` setup runs, DocuHarnessX shall not prompt for compliance topics and shall record none in scope.
5. DocuHarnessX shall persist the selection as a project file eligible for version control (not gitignored) and shall never persist it in `.env`.
6. The DocuHarnessX shall treat the published matrix as a self-assessment reference and shall label it as not a certification.

### Requirement 12: Self-assessment heatmap

**Objective:** As a reader, I want a traffic-light matrix of control pillars against the selected regimes, so that I can see coverage at a glance and skip what does not apply.

#### Acceptance Criteria

1. When at least one compliance topic is in scope, DocuHarnessX shall publish a matrix of shared control pillars (rows) against in-scope regimes (columns).
2. When a regime is not in scope, DocuHarnessX shall show that column gray (does not apply), including the whole PCI DSS column when PCI DSS was not selected.
3. When a pillar does not apply to a selected regime (for example cardholder-data environment outside PCI DSS), DocuHarnessX shall show that cell gray.
4. When a pillar applies to a selected regime, DocuHarnessX shall color the cell green, yellow, or red from automated repository evidence, unless the operator recorded an override.
5. When the operator recorded an override for a cell, DocuHarnessX shall use that status and shall still show the automated evidence as a note.
6. If no evidence is found for an in-scope applicable pillar, DocuHarnessX shall color that cell red, not gray.
7. The DocuHarnessX shall publish the matrix at adopter depth (1–2) and the per-cell evidence list at programmer depth (5–7).
8. When no compliance topic is in scope, DocuHarnessX shall omit the matrix rather than show an all-gray table.
